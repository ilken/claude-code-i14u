# Before Patching a Dependency

Before reaching for `yarn patch` (or `patch-package`), work through this checklist. Patches solve the immediate problem but add ongoing maintenance: every SDK upgrade re-applies the patch (and may silently fail if upstream code shifts). Often the same bug can be addressed in user code with comparable or lower effort.

Load this skill **whenever a task involves patching a third-party package**, or when a teammate (human or AI) proposes one. If you're triaging a CursorBot / automation-generated patch PR, run through this before approving.

---

## 1. Reproduce and locate every trigger

- [ ] **Reproduce the bug** with a clear repro before patching. A patch that suppresses a symptom you don't fully understand may mask other issues.
- [ ] **Find every call site** that triggers the bug. Don't stop at the first one — `grep` for the relevant package APIs.
- [ ] **Classify each call site:**
  - *Avoidable in user code* — the call pattern is incorrect or unnecessary; we can change our code.
  - *Inherent to the SDK* — the bug exists in any reasonable usage; only a patch or upstream fix can address it.

If **all** call sites are avoidable, prefer fixing them in user code (no patch).
If **some** are inherent, a patch may be justified — but combine it with code-level fixes where possible to minimize patch surface.

## 2. Check upstream

- [ ] **Read the package's CHANGELOG / GitHub releases** since your installed version. Has the bug been fixed in a later release?
- [ ] **Search the package's GitHub issues** for the error message or symptom. Has it been reported? Is there a maintainer-suggested workaround?
- [ ] **Check peer-dependency constraints.** Can you bump to the fixed version without breaking the wrapping library (e.g. `stream-chat-expo` pinning `stream-chat`)?

If a fixed release exists and is reachable, **bump the dependency instead of patching**.

## 3. Evaluate the patch itself

If a patch is still the right call:

- [ ] **Patch is minimal.** A one-line guard is fine; a 50-line refactor of upstream internals is a red flag.
- [ ] **Patch is logically safe.** The change should not alter business logic — it should narrow behavior (e.g. add a guard) rather than change semantics.
- [ ] **Patch is applied to all relevant build outputs.** ESM, CJS browser, CJS node — verify each one is updated, otherwise the patch only fires for some bundlers.

## 4. Required when shipping a patch

These are **non-negotiable**. A patch without these is technical debt that's invisible until it bites someone in 18 months.

- [ ] **File an upstream issue** on the package's GitHub repo with reproduction, stack trace, and the proposed fix. Even if you don't open a PR, this gets the bug on the maintainers' radar so it gets fixed for everyone — and gives you a stable URL to link from your tracking note. Search existing issues first; reuse if one already exists.
- [ ] **Link the upstream issue from your `resolutions` entry.** JSON doesn't support real comments, so use a top-level `_comments` object that yarn ignores. The link must point to the upstream issue (or PR) and state the drop conditions:

  ```json
  "resolutions": {
    "<package>@npm:^X.Y.Z": "patch:<package>@npm%3AX.Y.Z#~/.yarn/patches/<patch-file>.patch"
  },
  "_comments": {
    "resolutions/<package>": "Tracking upstream fix at https://github.com/<owner>/<repo>/issues/<n> (TICKET-XXXX). Drop this resolution and .yarn/patches/<package>-npm-*.patch once a release containing the fix is available and the dependency is bumped."
  }
  ```

  If the package isn't on GitHub, link wherever the upstream tracker lives (GitLab issue, mailing list, etc.).
- [ ] **Save a project memory** with the patch path, upstream issue link, and drop conditions, so future sessions can periodically revisit. (The `_comments` link is the dev-facing signal; the memory is the agent-facing signal.)
- [ ] **Reference the upstream issue from the PR description**, not just the package.json. Reviewers should see at a glance that a tracking link exists.

If the upstream maintainers later resolve the issue without a release, leave the patch and tracking note in place until the next major dependency bump — then remove together.

## 5. Triage prompts for AI-generated patches

When reviewing a patch PR generated by an automation (CursorBot, agent runs, etc.), ask explicitly:

1. *Did the agent enumerate every call site that triggers the bug?* — Often the patch hides multiple bugs at different sites; some may be fixable in user code.
2. *Did the agent check upstream for a release?* — Patches generated from RUM/error reports often skip this step.
3. *Did the agent file an upstream issue and link it from the resolutions block?* — If either is missing, do not merge until both exist (file the issue, add the `_comments` link).
4. *Does the PR description reference the upstream issue?* — If not, add it.

If any of these are missing, send the agent (or yourself) back through this checklist before approving.

---

## When to skip this checklist

- The bug is in **first-party code we own** (no patching involved).
- The fix is a **runtime config change** that the SDK already supports (e.g. a feature flag, an option you forgot to set).
- You've already gone through this checklist for the same package within the last few days and the situation hasn't changed.
